- E6 (the filter-semantics-plus-envelope problem), design half, is done, no code (Volume 5, section 4.11). This is the hardest honesty design in the project, and the honest outcome is a deferral with a documented ceiling, not a discovery rule. The census confirmed the filtered read is the majority of both apps' read APIs (pms roughly 42 list reads all filtered and `*ResultSet`-wrapped; erp roughly 30 filtered plus roughly 9 view or projection reads), and the design found a filter's meaning is not structurally provable in the general case. The three shapes resolved as: REFUSE for v1 (recommended, claims nothing, meets the never-claim constraint trivially); MODELED-OPAQUE rejected permanently (the copied parameter name is a claim in the tool schema regardless of any disclaimer, and pms cannot even write a truthful disclaimer since its filter semantics live in a hand-written `TenantQueryBuilder`, not in any query text); HUMAN-ATTESTED recorded as the one honest way to carry an unverified filter, deferred to its own future phase because it is the project's first human-in-the-loop and first carried-but-unproven claim, a real departure from structural-only. One narrow structural exception recorded: Spring Data derived-query filters (`findByNameContainingIgnoreCase`, `findByParentId`, `findByProductCategoryId`) are a framework contract, not nominal inference, so a verified-derived-query rule is the honest structural avenue if filtered discovery is ever pursued, but it is erp-shaped, a minority, and helps pms not at all. The envelope sub-problem (seeing a wrapped read; structurally solvable by unwrapping `*ResultSet` to its collection field and view element) is a prerequisite that pays off only once a representation exists, deferred with the rest. For v1, filtered, projected, and envelope reads stay named deferrals: no IR growth, no rule, no backend change, mis-bound 0. The ceiling (the structural-only tool tops out at unfiltered get-by-id and list-all; the filtered majority is beyond it) and the reopening triggers are in Volume 5 section 4.11; the census is in the ledgers (second-app-trial.md section 8.9, third-app-trial.md section 15). Since the recommendation is refuse-or-defer, no fixtures and no forecast are pre-registered.

## Reproduce the MVP

All paths are relative to the repository root. Build once. The example app's build runs the `tibyan-maven-plugin`, which scans the app's source and generates `tibyan/capabilities.json` onto its classpath (`target/classes/tibyan/capabilities.json`), so packaging is all that is needed:

```
mvn -q -DskipTests package
```

Then launch the app. It needs no manifest property, and its `application.yml` has no MCP block; the manifest is on the classpath because the build put it there:

```
java -jar examples/legacy-spring-app/target/legacy-spring-app-0.1.0.jar
```

The runtime finds the manifest on the classpath (verified: it logs `loaded 1 capability(ies) from class path resource [tibyan/capabilities.json]` then `registered 1 MCP tool(s): [getProduct]`, and Spring AI logs `Registered tools: 1`). The app starts on port 8080 with the MCP server at `http://localhost:8080/sse`. An MCP client (for example Claude Desktop) that calls getProduct with id 5 gets the real product, `{"id":5,"name":"Wireless Mouse","price":29.99}`, read from the real H2 store through ProductService.findById.

The CLI remains for manual and inspection use, and produces the same manifest:

```
java -jar tibyan-cli/target/tibyan-cli-0.1.0-jar-with-dependencies.jar scan examples/legacy-spring-app --out ./generated/legacy.ir.json

java -jar tibyan-cli/target/tibyan-cli-0.1.0-jar-with-dependencies.jar generate --backend mcp --ir ./generated/legacy.ir.json --out ./generated/legacy-mcp
```

To point the runtime at a manifest file for an ad hoc run, pass `-Dtibyan.capabilities`; on Windows PowerShell quote it: `java "-Dtibyan.capabilities=file:generated/legacy-mcp/tibyan/capabilities.json" -jar examples/legacy-spring-app/target/legacy-spring-app-0.1.0.jar`.
